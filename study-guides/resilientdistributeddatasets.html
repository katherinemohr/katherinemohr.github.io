Remembering the recipe, not the cake

Every cluster job used to reuse data by writing it to disk and reading it back — even between steps of the same iterative algorithm. RDDs keep data in RAM across operations instead, and recover from failure not by copying it, but by remembering exactly how to rebuild it.

📄 Zaharia, Chowdhury, et al. · "Resilient Distributed Datasets" · NSDI 2012 🎓 Intro systems/CS background assumed — the primers cover the rest ⏱ ~25 min read
📜

Log the recipe, not the cake.
Remember the deterministic steps that built a dataset — recompute only the piece you actually lost, instead of replicating everything just in case.

Before you begin

Just enough cluster-computing background

If you've used Hadoop, HDFS, or heard of a DAG scheduler, most of this will be review — skim it. If not, these four cards cover exactly what the paper assumes. Collapsed by default; open whatever's unfamiliar.

1MapReduce, Dryad, and why "reuse" means round-tripping through disk▾

MapReduce (Dean & Ghemawat) and Dryad split a computation into high-level parallel operators, hiding work distribution and fault tolerance from the programmer. Fault tolerance in these systems is cheap because it's built on re-execution: if a task fails, just re-run it from its original input (Section 1).

The catch: the only sanctioned way to pass data from one job to the next is to write it out to a distributed filesystem (e.g. HDFS) and read it back in the next job. That costs disk I/O, replication, and serialization every single hop (Section 1). For a one-shot batch job, fine. For an iterative algorithm that reruns the same computation over the same data 10–100 times — gradient descent, PageRank, k-means — you pay that toll on every iteration, even though nothing about the data actually needs to leave memory.

Now you're ready: the entire paper is about closing this one gap — letting a cluster job keep data resident in RAM across operations, safely.
2HDFS, blocks, and data locality▾

The Hadoop Distributed File System stores a file as fixed-size blocks (256 MB in this paper's experiments), replicated across several machines for durability. A scheduler tries to run each task on a machine that already holds the block it needs — data locality — to avoid shipping data over the network.

RDDs inherit this idea directly: every RDD can report preferred locations for each of its partitions (e.g., "this partition's data lives on nodes A and B"), and Spark's scheduler uses that to place tasks (Section 5.1, Table 3).

Now you're ready: when the paper says an RDD "knows which machines each block is on," this is the mechanism.
3DAGs and lazy evaluation▾

A directed acyclic graph (DAG) of operations lets a system record a computation's structure before running any of it, so it can optimize across steps instead of executing them eagerly one at a time. DryadLINQ builds such a DAG from a program's high-level operators.

Spark does the same: an operation that only defines a new dataset (without computing it yet) is lazy. Nothing runs until something actually needs an output. This is what lets Spark fuse several lazy steps into a single pass over the data rather than materializing every intermediate result (Section 2.2, Section 5.1).

Now you're ready: in the code examples ahead, a line like lines.filter(...) does zero cluster work by itself — it just extends the DAG.
4Closures — how "code" gets shipped to a cluster▾

Spark's API is embedded in Scala. Writing rdd.filter(x => x.contains(query)) passes a closure — a function literal that captures variables (here, query) from its surrounding scope. Spark serializes each closure as a Java object and ships it to worker machines, so the same user-written function can run against remote partitions of data (Section 3, footnote 2).

You don't need Scala fluency for what follows — just keep in mind that the little snippets you'll see (map, filter, reduce) are ordinary functions being shipped across the network, not magic.

Now you're ready: "transformation" in the next tabs just means "one of these shippable functions, applied to every element of a dataset."
The whole story in one place

RDDs, in a nutshell

The problem, the fix, and the result.

Cluster frameworks like MapReduce and Dryad give you rich parallel operators, but the only way to reuse data across computations is to write it to stable storage and read it back — expensive I/O, replication, and serialization on every hop, paid again and again by iterative algorithms and interactive queries that touch the same data repeatedly (Section 1). Systems that instead keep data in mutable shared memory (distributed shared memory, key-value stores, Piccolo) solve the reuse problem, but their fault tolerance requires either replicating every write across machines or logging updates and rolling back a checkpoint — both expensive, because they move real data over a network whose bandwidth is far below RAM's (Section 1, Table 1).

Resilient Distributed Datasets (RDDs) cut a different path (Section 2.1): an RDD is a read-only, partitioned collection that can only be built by loading data from stable storage or by applying a deterministic transformation (map, filter, join, …) to existing RDDs. Because the only way to "write" one is through a bulk, deterministic operation, Spark never needs a second physical copy for safety — it just remembers the recipe (lineage): which transformation, applied to which parent. If a partition is lost, Spark re-applies the recipe to rebuild just that partition, in parallel with everything else that's still healthy.

The payoff: in the system built on this idea, Spark, iterative machine learning and graph workloads run up to 20× faster than Hadoop (Section 6.1), a production analytics report sped up 40× (Section 6.5), and Spark can interactively query a 1 TB dataset in 5–7 seconds (Section 6.6) — while the same restricted abstraction turns out to be expressive enough to implement MapReduce, Pregel, HaLoop, and SQL-style queries as small libraries on top of one runtime (Section 7.1).

🍯 Key takeaways

  • Prior systems pay disk I/O, replication, and serialization every time data crosses between jobs; RDDs let you persist data in memory and reuse it directly.
  • An RDD can only be built via deterministic bulk transformations — this restriction is exactly what makes it cheap to reconstruct.
  • Lineage (the transformation recipe) is typically kilobytes, even for datasets spanning 100 GB (Section 6.3) — log the recipe, not the cake.
  • Narrow dependencies (map, filter) recover cheaply and in parallel; wide dependencies (groupByKey, join) can require recomputing an entire ancestor.
  • Immutability is also what makes speculative "backup tasks" for straggling machines safe — nothing to corrupt (Section 2.3).
  • Result: up to 20–40× speedups, and one abstraction that reproduces MapReduce, Pregel, and HaLoop as ~200-line libraries (Section 7.1).
Six everyday pictures

How to think about lineage and dependencies

The paper itself is fairly spare with analogies — its main comparison is the RDD-vs-DSM table (Table 1). The pictures below are illustrative devices to build intuition, each grounded in a specific section, with an honest note on where the picture stops being true.

The core mapping · Lineage as a recipe

A recipe, not a photograph of the cake

A recipe is a small, exact set of deterministic steps; the cake itself is large and, once eaten, gone for good unless you bake another. An RDD's lineage is the recipe — "load this file, then filter, then map" — small enough to log cheaply (often under 10 KB, Section 6.3), even when the "cake" it describes is a 100 GB dataset.

Where it holds tightly: exactly like a recipe, lineage only works because each step is deterministic — the same inputs always yield the same outputs (Section 2.1).
Narrow dependency · Assembly line

One station, one input, no coordination

On an assembly line, each station only ever needs the part sitting directly in front of it — never a part from another station's lane. A narrow dependency (map, filter) is the same: each child partition depends on exactly one parent partition, so if a station's part is lost, replacing it needs no help from any other lane, and every lane can be repaired in parallel (Section 4, Fig. 4).

Where it holds tightly: this is exactly why narrow-dependency recovery is "fine-grained and low-overhead" (Table 1) — no cross-machine coordination needed.
Wide dependency · A potluck table

Everyone's dish has to reach the shared table first

A potluck needs every dish physically gathered onto one table before anyone can serve a plate — no way to plate food that's still scattered across everyone's kitchens. A wide dependency (groupByKey, non-co-partitioned join) needs data from all parent partitions gathered ("shuffled") before any child partition can be computed (Section 4, Fig. 4–5). If one dish never arrives, plating can't finish — and re-cooking it might mean re-cooking from a table that's now also missing pieces.

Where it's sharper than the analogy: losing one parent partition under a wide dependency can force recomputing a slice from every ancestor, not just one dish (Section 5.4) — potlucks are rarely that fragile.
Straggler mitigation · Running two racers

It's safe to run the same leg twice

If a race lets you send a second runner down the same lane the moment the first looks slow, and both runners finishing just means you take whichever crossed first — nothing breaks, because neither runner can interfere with the other. Spark does exactly this with slow tasks: launch a backup copy elsewhere and take whichever finishes first (Section 2.3), safe only because RDDs are immutable — two copies of a task can't corrupt shared state the way two writers to the same memory cell could.

Where it's sharper than the analogy: the paper explicitly contrasts this with distributed shared memory, where backup tasks "would be hard to implement with DSM, as the two copies [of a task] would access the same memory locations and interfere with each other's updates" (Section 2.3).
Checkpointing vs. lineage · Insurance vs. repair

Paying premiums forever vs. paying only when something breaks

Full replication is like buying comprehensive insurance and paying the premium constantly, whether or not anything ever goes wrong. Lineage-based recovery is like skipping the policy and just paying to repair the one thing that actually breaks, when it breaks. For RDDs with only narrow dependencies (like points in logistic regression), "checkpointing may never be worthwhile" (Section 5.4) — repair is already cheap. For long wide-dependency chains (like PageRank's ranks), the premium starts looking worth it, which is exactly why Spark offers an optional checkpointing flag.

Where it's narrower: Spark's checkpointing is a manual choice via a flag to persist (Section 5.4) — the paper describes automatic checkpoint selection as future work, not something Spark decided for you.
Where it breaks · No single-cell edits

A recipe can't describe "change just this one bite"

A recipe (lineage) describes how to bake a whole batch, not how to swap out one raisin after the fact. RDDs are only ever written via bulk, deterministic transformations over an entire dataset — there's no operation for "update this one record." The paper is explicit that this makes RDDs a poor fit for a web application's backing store or an incremental crawler updating individual records (Section 2.4).

Consequence: for exactly that class of application, the paper points to fine-grained systems like databases, RAMCloud, Percolator, and Piccolo instead (Section 2.4) — RDDs and those systems are meant to coexist, not compete.
The full explanation

How it actually works

Section by section, with an interactive failure simulator you can drive yourself.

1 · The problem — reuse means a round trip through stable storage

MapReduce and Dryad give programmers rich parallel operators and hide fault tolerance behind re-execution, but the only sanctioned way to share data between two jobs is to write it to a distributed filesystem and read it back (Section 1). That is fine for one-shot batch pipelines, but ruinous for two workloads the paper singles out: iterative algorithms (PageRank, k-means, logistic regression — the same data touched 10s to 100s of times) and interactive data mining (many ad-hoc queries against the same working set). Systems that instead expose fine-grained mutable shared memory — distributed shared memory, key-value stores, Piccolo — solve reuse, but only by accepting expensive fault-tolerance machinery: replicate every write across the network, or log updates and roll back a checkpoint (Section 1, Table 1).

⚠
Why not just cache the data flow system's output in RAM naively? Section 2.3 spells out the actual comparison: distributed shared memory's fine-grained writes mean the only ways to survive a failure are checkpoint-and-rollback (expensive, and requires pausing the whole program to snapshot) or full replication (expensive, network-bound). RDDs sidestep both by restricting how data can be created in the first place.

2 · The RDD abstraction and lineage

An RDD is a read-only, partitioned collection of records, created only by (1) loading data from stable storage, or (2) applying a deterministic transformation — map, filter, join, and friends — to one or more existing RDDs (Section 2.1). Because those are the only two ways an RDD can come into existence, every RDD can name its own recipe: the transformation and the parent(s) it was built from. That recipe is its lineage. Users additionally control two independent knobs per RDD: persistence (persist() — keep it in memory, on disk, or replicated, rather than recomputing it every time it's touched) and partitioning (hash- or range-partition key-value RDDs, which matters enormously for join, Section 2.1).

Figure 1's log-mining pipeline makes lineage concrete: lines (an HDFS file) → errors (filter) → HDFS errors (filter) → time fields (map). Lose a partition of HDFS errors, and Spark doesn't reach for a replica — it re-applies the two filters to the matching partition of lines.

3 · Narrow vs. wide dependencies — the fact that decides recovery cost

Section 4 classifies every dependency between an RDD and its parent into one of two kinds. A narrow dependency means each parent partition feeds at most one child partition (map, filter, a co-partitioned join). A wide dependency means a parent partition can feed multiple child partitions (groupByKey, a join whose inputs aren't co-partitioned) — see Figure 4. This single distinction drives two separate things at once: whether Spark can pipeline operations in one pass on one machine (narrow) or must insert a network shuffle (wide) — the basis for the staged DAG execution in Figure 5 — and how expensive failure recovery is. Narrow-dependency recovery recomputes only the lost partition, in parallel with everything else. Wide-dependency recovery can require recomputing a slice from every ancestor partition, because a single lost partition may have contributed to many children (Section 4, Section 5.4).

4 · Recomputation vs. checkpointing

Since RDDs are immutable, checkpointing them is simpler than checkpointing general shared memory: Spark can write an RDD to stable storage in the background, with no program pause and no distributed-snapshot protocol (Section 5.4). Spark exposes this as a REPLICATE flag to persist, but leaves the choice of what to checkpoint to the user — automatic selection is future work. The paper's own guidance (Section 5.4): checkpoint RDDs with long, wide-dependency lineage chains (PageRank's ranks); for RDDs with narrow dependencies back to stable storage (logistic regression's points, PageRank's links), "checkpointing may never be worthwhile," because lineage recovery is already cheap and parallel. (Separately, Section 3.2.2 mentions a RELIABLE flag for replicating specific iterations' data to cut recovery time in long-running jobs — the paper doesn't fully reconcile the naming of these two mechanisms, but the underlying idea in both cases is: pay a storage cost now to avoid a larger recomputation cost later.)

5 · Scheduling, memory management, and stragglers

When an action runs, Spark's scheduler walks the target RDD's lineage backward and builds a DAG of stages (Section 5.1, Fig. 5): each stage packs together as many pipelined narrow-dependency transformations as possible, and stage boundaries fall exactly at wide dependencies (which need a shuffle) or at already-cached partitions (which let the scheduler skip recomputing an ancestor entirely). Tasks are placed using data locality, same as HDFS-aware schedulers. Persistent RDDs are kept under an LRU eviction policy at the granularity of whole RDDs — evicting the least-recently-used RDD's partitions, with one exception: Spark won't evict a partition to make room for another partition of the same RDD, since most operations scan an entire RDD and that partition will likely be needed again soon (Section 5.3). Because RDDs are immutable, Spark can also safely re-run a slow task as a speculative backup, exactly as MapReduce does for stragglers (Section 2.3) — something the paper argues is difficult in distributed shared memory, where two copies of a task would race on the same mutable state.

6 · One abstraction, many programming models

Section 7.1 argues RDDs can express, "efficiently" (meaning: not just the same output, but the same optimizations), several models previously built as separate systems: MapReduce (flatMap + groupByKey, or reduceByKey with a combiner), DryadLINQ (its bulk operators map directly onto RDD transformations), SQL (data-parallel operations over sets of records), Pregel (store each superstep's vertex states in an RDD; a bulk flatMap generates the messages for the next step — implemented as a ~200-line library), and iterative MapReduce systems like HaLoop and Twister (also reimplemented as a ~200-line library on Spark). The paper's explanation for why one restricted abstraction generalizes this far: bulk transformations aren't actually a limitation for most parallel programs, because most parallel programs already apply the same operation to every record; and immutability isn't an obstacle either, because you can always represent "the next version" as a new RDD (Section 7.1) — indeed, many MapReduce jobs already run against filesystems, like HDFS, that don't support in-place updates at all.

Where the abstraction breaks

The paper is candid about scope (Sections 2.4, 5.1, 5.3, 7.2):

⚠
No fine-grained writes. RDDs are unsuitable for applications needing asynchronous, fine-grained updates to shared state — a web application's backing store, or an incremental crawler updating individual records. The paper names databases, RAMCloud, Percolator, and Piccolo as the right tools for that job instead (Section 2.4).
⚠
Lineage-based recovery assumes determinism. A nondeterministic transformation (e.g., a map with side effects) won't be replayed correctly — at best the system can detect and report the nondeterminism via checksums, not correct for it (Section 7.2, footnote 9).
⚠
Gaps acknowledged as of publication. Scheduler failures aren't yet tolerated ("we do not yet tolerate scheduler failures," Section 5.1), and each Spark instance keeps its own separate memory space, with cross-instance sharing left as future work (Section 5.3).
Follow the pipeline, step by step

One log-mining query, from code to recovery

Built from the paper's own log-mining example (Section 2.2.1, Fig. 1), then extended with the paper's actual measured fault-recovery numbers (Section 6.3, Fig. 11) and its PageRank partitioning result (Section 3.2.2, Section 6.2).

① Define the pipeline — and do zero work

// nothing runs yet — these are lazy transformations
val lines  = spark.textFile("hdfs://...")
val errors = lines.filter(_.startsWith("ERROR"))
errors.persist()   // ask Spark to cache this RDD in RAM once computed
  1. lines is an RDD over an HDFS file; errors is a narrow-dependency filter of it. Because filter is a transformation, not an action, no cluster work has happened yet (Section 2.2.1).

② Trigger an action — now the DAG runs, pipelined

errors.count()   // action: forces computation
errors.filter(_.contains("MySQL")).count()                                // query A
errors.filter(_.contains("HDFS")).map(_.split('\t')(3)).collect()   // query B
  1. count() builds the DAG for errors, sees a single narrow-dependency hop from lines, and pipelines the read-plus-filter into one pass per HDFS block — no shuffle needed.
  2. Query A and query B both build on the already-cached errors, instead of re-scanning and re-filtering the raw logs — this is the whole data-reuse gap the paper set out to close.

③ A node fails mid-query — recompute one partition, not the dataset

  1. Suppose a machine holding a partition of errors dies during query B. There's no replica to fall back on — Spark reads errors's lineage ("partition i = filter(partition i of lines, startsWith)") and re-applies that filter to the matching block of lines, which HDFS still holds safely. Only that one partition is rebuilt, in parallel with the rest of the query proceeding normally.
  2. This is exactly the mechanism the paper measures directly with k-means (Section 6.3, Fig. 11): across 10 iterations on 75 nodes, each iteration held steady at ~58 seconds — until a node was killed at the start of iteration 6, which rose to 80 seconds while the lost partitions were rebuilt from lineage, then dropped straight back to 58 seconds the very next iteration. No checkpoint replay, no rollback of the whole job.
  3. For scale: the paper notes the lineage graphs in these examples were typically under 10 KB, even though the dataset itself was 100 GB (Section 6.3) — the recipe really is that much smaller than the cake.

④ Add partitioning — PageRank's join gets cheaper, not just its recovery

val links = spark.textFile(...).map(...)
             .partitionBy(myPartFunc).persist()   // hash-partition by URL
  1. If links and ranks are both hash-partitioned by URL, each iteration's join between them becomes a narrow dependency — a URL's link list and its rank already live on the same machine, so no shuffle is needed at all (Section 3.2.2).
  2. Measured effect (Section 6.2, Fig. 10): in-memory storage alone gave PageRank a 2.4× speedup over Hadoop on 30 nodes; adding consistent partitioning pushed that to 7.4×.
  3. Without matching partitioning, that same join is a wide dependency requiring a full network shuffle every single iteration — the difference between "assembly line" and "potluck," from the Analogies tab, made concrete.

Check your understanding

Practice

Try each before opening the answer.

Q1
Why can RDDs recover from a lost partition without replicating data, when a distributed shared memory (DSM) system generally can't?
Show answer
Because RDDs are only ever built via deterministic bulk transformations from stable storage or other RDDs, the system can log the recipe (lineage) instead of the data itself, and rebuild exactly the lost partition by replaying that recipe on the parent's data. DSM allows arbitrary fine-grained writes to shared state, so there's no compact recipe to replay — the only options left are checkpoint-and-rollback or full replication (Table 1, Section 2.3).
Q2
A join between two RDDs can be either a narrow or a wide dependency. What determines which?
Show answer
Whether the two parent RDDs are already partitioned the same way (e.g., both hash-partitioned by the join key). If so, each partition of one parent only needs the corresponding partition of the other — narrow. If not, matching keys can live on arbitrary machines across both parents, requiring a shuffle to bring them together — wide (Section 4, Fig. 4).
Q3
In the PageRank example, why doesn't the links RDD need replication for fault tolerance, while ranks might benefit from checkpointing?
Show answer
links is derived from stable storage via a narrow-dependency map, so a lost partition can be cheaply recomputed in parallel by re-reading and re-mapping the corresponding input block. ranks is rebuilt every iteration via a join/reduceByKey over the previous iteration's ranks and contribs — a chain of wide dependencies that grows with each iteration, so recovering a late iteration's ranks could mean recomputing a long, wide-dependency chain. Checkpointing breaks that chain (Section 3.2.2, Section 5.4).
Q4
Why are Spark transformations lazy instead of executing immediately when called?
Show answer
Laziness lets Spark build the full lineage/DAG before doing any work, so when an action finally triggers computation, the scheduler can pipeline narrow-dependency steps into a single pass per partition and skip recomputing anything already cached — instead of eagerly materializing every intermediate RDD (Section 2.2, Section 5.1).
Q5
Spark beat even HadoopBinMem — Hadoop with data already converted to binary and cached in an in-memory HDFS — by roughly 20× on logistic regression. If the data was already in memory for both systems, where does that gap come from?
Show answer
Not from disk I/O — from three other overheads Hadoop still pays even with in-memory binary data: minimum per-job startup/coordination overhead (~25s measured via no-op jobs), overhead inside HDFS's own serving path (memory copies plus a checksum, ~2s), and the cost of deserializing binary records into usable Java objects (~3s). Spark avoids all three by keeping RDD elements as live, already-deserialized Java objects in its own memory (Section 6.1, Fig. 9).
Q6
What kind of application does the paper explicitly say RDDs are a bad fit for, and why?
Show answer
Applications needing fine-grained, asynchronous updates to shared state — e.g., the backing store for a web application, or an incremental web crawler updating individual records as new data arrives. RDDs can only be "written" via coarse-grained, deterministic transformations applied to whole datasets, so there's no efficient way to express a single targeted update to one record (Section 2.4).
Look it up

Glossary, limitations & further reading

Core terms
RDDResilient Distributed Dataset — an immutable, partitioned collection built only via deterministic transformations from stable storage or other RDDs (Section 2.1).
TransformationA lazy operation defining a new RDD from existing ones (map, filter, join, …) — no computation happens until an action needs the result.
ActionAn operation that triggers computation and returns a value to the driver or writes to storage (count, collect, reduce, save).
LineageThe recorded chain of transformations that produced an RDD — the "recipe" used to recompute lost partitions instead of replicating data.
PartitionAn atomic chunk of an RDD's data — the unit of parallel computation and of failure recovery.
Narrow dependencyEach parent partition feeds at most one child partition (map); enables pipelining and cheap, parallel recovery.
Wide dependencyA parent partition may feed multiple child partitions (groupByKey, non-co-partitioned join); needs a shuffle and can force expensive recovery.
PersistThe API call marking an RDD for retention (memory, disk, or replicated) across operations, instead of recomputing it from lineage every use.
Supporting terms
DriverThe user's program — defines RDDs, tracks lineage, and dispatches actions to workers (Section 3).
StageA batch of pipelined, narrow-dependency tasks in the DAG scheduler; boundaries occur at wide dependencies (shuffles) or already-cached partitions (Section 5.1, Fig. 5).
StragglerAn unusually slow task/machine; mitigated, as in MapReduce, by speculatively running a backup copy — safe because RDDs are immutable (Section 2.3).
ShuffleThe network data movement required at a wide dependency, analogous to MapReduce's shuffle between map and reduce.
LRU eviction (at the RDD level)Spark's default memory-management policy for persisted RDDs; won't evict a partition to make room for another partition of the same RDD (Section 5.3).
CheckpointingOptionally writing an RDD to stable storage (a REPLICATE flag to persist) to shorten recovery for long, wide-dependency lineage chains (Section 5.4).
ClosureA function literal (e.g., inside map/filter) that captures variables from its scope; Spark serializes closures to ship user code to workers (Section 3).
Sequence group (Pregel-on-Spark)Not an RDD term — a reminder that "superstep" vocabulary from Pregel maps onto per-iteration RDDs when Pregel is implemented as a library over Spark (Section 7.1).
Limitations & open questions
📌
Stated by the authors: RDDs target batch applications that apply the same operation to a whole dataset; fine-grained asynchronous updates are explicitly out of scope (Section 2.4). Checkpoint selection is manual, not automatic, as of this paper (Section 5.4). Scheduler failures aren't yet tolerated, and cross-instance memory sharing is future work (Section 5.1, 5.3). Lineage-based recovery and the proposed RDD debugger both assume deterministic transformations (Section 7.2, footnote 9).
🔍
Worth flagging (observations, not the paper's own claims): the paper doesn't give a systematic decision rule for exactly when checkpointing pays off versus lineage recomputation beyond the PageRank/logistic-regression contrast — Young's checkpoint-interval result [30] is cited but not applied concretely. The headline speedups are measured against Hadoop 0.20.2 and a self-built HadoopBinMem baseline, not against later data-parallel systems, including Spark's own later evolution. The paper doesn't discuss what happens if lineage chains themselves become the bottleneck to track (beyond noting they stay small in its examples).
