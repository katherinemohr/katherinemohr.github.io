ASPLOS 2025 · A Field Guide

Fusing what stays on one processor, not what secretly needs a network hop

Distributed array libraries turn a + b into a stream of parallel tasks handed to a runtime like Legion. Diffuse rewrites that stream before Legion ever sees it — fusing tasks into one pass over memory, but only when a cheap, provably sound check confirms no processor needs data from its neighbor.

📄 Yadav, Sundram, et al. · "Diffuse" · ASPLOS 2025 🎓 PL background assumed (IRs, dataflow analysis, alpha-equivalence) — primers cover the systems side ⏱ ~35 min read
🧩

Fusible iff every processor's work depends on only its own prior work — never a neighbor's.
Checked in constant time, regardless of GPU count — that's what "scale-free" buys you.

Before you begin

The systems background this paper assumes

This paper leans on PL machinery (IRs, dependence analysis, alpha-equivalence) more than most systems papers, and explains the systems side more. These three cards cover the systems side. Collapsed by default; open whatever's unfamiliar.

1Distributed task-based runtime systems▾

"Scale-out" array-processing systems — the paper's running examples are cuPyNumeric (a distributed drop-in replacement for NumPy) and Legate Sparse — don't hand-parallelize your code. Instead, the library translates each high-level call (a + b, np.linalg.norm) into one or more tasks — units of work over a slice of data — and hands a stream of tasks to a runtime system, here Legion (Bauer et al. 2012). The runtime decides which tasks can run in parallel, on which nodes, and inserts whatever communication is required because two tasks touch overlapping data.

This is the systems analogue of a PL "runtime managing effects": library authors write sequential-looking task bodies, and the runtime is responsible for cross-node consistency, the way a language runtime handles memory management so the programmer doesn't have to. Independently-developed libraries can be composed freely because the runtime — not each library — owns correctness.

Now you're ready: keep Legion and Diffuse apart in your head. Legion actually executes tasks and computes fine-grained dependencies at scale. Diffuse sits above Legion — it intercepts the task stream first, rewrites it (fusing tasks), and only then hands the optimized stream down. Diffuse never replaces Legion's own dependence tracking; it just shrinks what Legion has to deal with (Section 1).
2Weak scaling and GPUs▾

The paper's benchmarks run on a cluster of nodes with 8 GPUs each (Section 7). A weak-scaling experiment grows the problem size in proportion to the machine size, so the amount of work per processor stays fixed — the reported metric is throughput per processor, and the ideal outcome is a flat line as you add machines. This differs from strong scaling (fixed total problem size, more processors = faster).

Now you're ready: a benchmark can look excellent on 1 GPU but disappointing at 128 GPUs simply because there's less fusable work per GPU once the data is chopped finer — this happens for the CFD benchmark in Key Results.
3MLIR and dialects▾

MLIR (Multi-Level IR) is LLVM-based compiler infrastructure. The one thing to know: MLIR lets a single program mix multiple dialects — sub-languages with their own typed operations (e.g. memref for array-like memory, affine for loop nests amenable to polyhedral analysis, arith for scalar arithmetic) — that a shared set of compiler passes can rewrite and lower together.

Now you're ready: Diffuse leans on this to represent a task's body once as MLIR and let generic loop-fusion/parallelization passes operate on it, instead of writing its own compiler backend from scratch (Section 6).
The whole story in one place

Diffuse in a nutshell

The problem, the fix, and the result.

Diffuse automatically fuses operations in distributed, GPU-accelerated Python programs (built on libraries like a distributed NumPy) — without the programmer changing any code. "Fusing" means merging several separate parallel operations into one, so intermediate arrays are never materialized and data is read from memory once instead of many times.

The central technical problem: fusion is easy to get right on a single machine but easy to get wrong for a cluster. Fusing two operations that secretly require communication between nodes produces a wrong (or deadlocking) program. Diffuse's contribution is (1) a compact intermediate representation of distributed computation whose size doesn't grow with the number of machines (scale-free), and (2) a fusion analysis over that IR that can be checked cheaply, is provably sound, and composes with an MLIR-based compiler that does the low-level kernel merging (§3–6).

The payoff: Diffuse speeds up seven unmodified distributed applications by 1.86× on average (geometric mean) across up to 128 GPUs, matches or exceeds PETSc (MPI+C) by 1.4×, and even beats hand-optimized code by 1.23× on average — by finding fusion opportunities a human missed (Abstract, §1).

🍯 Key takeaways

  • Fusing across a cluster is only safe when no processor needs another processor's data — that's the entire correctness question this paper formalizes.
  • Diffuse's IR is scale-free: a symbolic representation whose size never grows with GPU count, so the fusion check stays cheap at any scale.
  • Fusibility (Definition 3): a dependence map that's at most the identity — every processor depends only on itself.
  • Checking that directly is as expensive as the thing being avoided, so Diffuse uses four sound-but-incomplete syntactic constraints instead, each checkable in constant time.
  • Task fusion alone barely helps; the real win comes from MLIR kernel fusion, which merges loop bodies and deletes now-local intermediate buffers.
  • Result: 1.86× geomean over unmodified code, 1.4× over PETSc, 1.23× over hand-optimized code — up to 10.7× on the best case.
Six everyday pictures

How to think about Diffuse's design

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The system boundary · An editor before the printer

An editor who reorganizes chapters before the printer sees them

An editor can merge, reorder, or cut chapters before a manuscript ever reaches the printing press — the press itself doesn't need to know editing happened, it just prints what it's handed. Diffuse plays the editor: it intercepts the task stream before Legion (the printer — the runtime that actually executes tasks and computes fine-grained dependencies) ever sees it, rewrites it by fusing tasks, and only then hands the optimized stream down (§1).

Where it's precise: Diffuse never replaces or reimplements Legion's own dependence tracking. It only shrinks what Legion has to deal with, using its own cheaper, coarser (scale-free) analysis (§4.4).
The IR · Scale-free

A blueprint that doesn't grow when you build more copies

A building's blueprint has a fixed size whether you construct one copy or a thousand — it describes the shape of the building, not each instance. Diffuse's IR does the same for parallel tasks: a partition is a symbolic function from processor index to sub-store, not an explicit table of which indices go where, and an index task stores a symbolic domain size, not one entry per point task (§3). Two partitions of the same kind compare for equality in constant time.

The cost of this economy: only partition kinds with constant-time equality checks are usable — the paper presents two (None, Tiling) and notes others exist "with no additional technical insight," an assertion it doesn't independently substantiate (§3.1).
Fusibility · Own inbox only

Each worker waits only on their own inbox

On an assembly line, a station can start the moment it wants if it never needs a part from a different station's output bin — needing your own bin's previous contents is fine; reaching into a neighbor's bin means you must wait for them. Definition 3 formalizes exactly this: two tasks are fusible iff every processor's work in the second task depends on at most that same processor's work in the first — never a neighbor's (§4.1–4.2). Reach into a neighbor's bin (the dashed red line) and fusion is unsafe.

Where it's precise: this is standard true/anti/reduction dependence analysis (Aho–Lam–Sethi–Ullman) lifted from statements to per-processor point tasks — the same three classic hazards, just checked processor by processor.
Sound but not complete · The strict inspector

An inspector who only signs off on what they can prove

A strict building inspector approves a design only if they can prove safety directly from the blueprint — a design that's actually safe, but in a way the inspector's checklist can't verify, gets rejected anyway. Diffuse's four syntactic constraints are exactly this: sound (never approve an unsafe fusion) but not complete (some genuinely safe fusions get rejected because they don't match the checklist). Theorem 1 proves the sound half only — the paper explicitly disclaims completeness (§4.2.1, §4.3).

Where it's precise: this is the same trade-off every conservative static analysis or sound type system makes — reject some valid programs in exchange for a proof that nothing unsafe ever slips through.
Temporary elimination · Escape analysis

Promoting a heap allocation to a register

A compiler's escape analysis proves a value never outlives its function and promotes it from a heap allocation to a stack slot or register — no garbage collector needed, because nothing outside can ever see it. Temporary elimination is the distributed-systems version: if a store is entirely produced and consumed inside the fused region, no later pending task reads it, and the application holds no live reference to it (Definition 4), Diffuse demotes it from a real distributed array to a task-local, on-the-fly buffer — it's never actually allocated (§5.1).

Where it's precise: exactly like escape analysis, all three conditions must hold — a single still-pending reader (like norm reading part of w in the paper's example) is enough to force real allocation.
Memoization · Alpha-equivalence

λx.x and λy.y are "the same" program

λx. x and λy. y compute the identical function — they differ only in what the bound variable happens to be called. Diffuse treats re-running the same loop's task stream the same way: it canonicalizes each stream window to a De Bruijn-index-like numbering of stores (first store mentioned → 0, next new one → 1, …), so two windows that are "the same shape, different IDs" canonicalize identically and reuse the previous fusion decision without redoing the analysis (§5.2, Figure 7).

Where it's precise: this is literally alpha-equivalence checking, not an analogy to it — the paper names it as such.
The full explanation

How it actually works

Section by section, with an interactive fusibility checker you can drive yourself.

1 · Why is distributed fusion hard?

Consider a five-point stencil update on a distributed 2D grid (Figure 1, §2) — a classic PDE-solver kernel:

avg = center + north + east + west + south
work = 0.2 * avg
center[:] = work

center, north, east, west, south are all aliased views of one distributed array, shifted by one cell in each direction. Executed literally, this issues one task per +, one for the scalar multiply, one for the copy — each allocating a fresh distributed temporary. Diffuse rewrites this into a single FUSED_ADD_MULT task — a 4× speedup on this loop body.

⚠
But the final line doesn't fuse in — and this is the crux of the whole paper. center is a subset of the same underlying array as the four views being read. Fusing the write to center into the task that reads them would create a single task concurrently writing to and reading from overlapping memory across node boundaries — a race, not merely an inefficiency. The question the whole paper answers formally: given a stream of distributed tasks that may arbitrarily alias, how do you decide, cheaply and correctly, which prefix can be fused without changing what any node observes (§2)?

2 · The IR — making "cheaply" possible

Checking fusibility by literally comparing, for every pair of processors, which array elements they touch would cost more as processor count grows — hopeless at 128 GPUs. Diffuse keeps everything scale-free: the size of the representation doesn't depend on how many pieces the data is partitioned into (§3).

Two constructs carry this. A store is a distributed array — an ID plus a rectangular shape (domain). A partition is a symbolic function from points in a launch domain to sub-stores, not an explicit table. The paper presents two kinds: None (replicate to every point) and Tiling(shape, offset, proj) — an affine tiling optionally preceded by a projection function that can drop dimensions, which is exactly how the aliased stencil views are expressed compactly. Two partitions of the same kind check for equality/aliasing in constant time (§3.1). An index task IndexTask(domain, args) represents a whole SPMD-style group of parallel point tasks, one per point in domain, each reading/writing/reducing its sub-store under a stated privilege — and its size on paper depends only on the symbolic domain, never an enumeration of tasks (§3.2).

⚖️
The trade-off: only partition kinds supporting constant-time equality are usable. Legion itself supports arbitrary index-set partitions — more flexible, but then the aliasing queries needed for fusion scale with the degree of parallelism (§4.4, §8). Diffuse trades partition generality for compile-time-cheap analysis.

3 · When can two tasks be fused?

This is standard dependence analysis (following Aho, Lam, Sethi & Ullman) lifted to a distributed, task-parallel setting — but asked per-processor: does the point task at processor p′ in the second index task depend on the point task at processor p in the first? For two point tasks with overlapping sub-stores of the same parent, a dependence exists under one of three classic hazards (Definition 1):

  • true-dep (RAW/WAW-like): T₁ writes S, T₂ reads/writes/reduces overlapping S′.
  • anti-dep (WAR-like): T₁ reads S, T₂ writes/reduces overlapping S′.
  • reduction-dep: T₁ reduces S, T₂ reads/writes overlapping S′.

(Two tasks that both merely read, or both reduce with the same associative-commutative operator, are exempt.) Collecting these into a dependence map D(T₁,T₂): domain(T₁) → 𝒫(domain(T₂)) gives:

🍯
Definition 3 (fusibility). T₁ and T₂ are fusible iff, for every point p, D(T₁,T₂)[p] ⊆ {p} — every processor's work in T₂ depends on at most its own corresponding work in T₁, never another processor's.

Materializing D directly costs the same as the thing being avoided, so Diffuse never computes it. Instead it uses four sufficient — sound but not complete — syntactic constraints, each checkable with the scale-free IR's constant-time partition-equality test (§4.2.1):

ConstraintWhat it rules out
launch-domain-equivalenceTasks over different-shaped/sized launch domains — data movement is generically needed to reconcile them.
true-dependenceA task writes S via partition P, a later task reads/writes S via a different, aliasing partition P′. Same partition is fine — still point-wise.
anti-dependenceA task reads S via P, a later task writes S via a different partition P′.
reductionA task reduces into S, and any other task (before or after) reads or writes any view of S — you can't observe a partially-completed reduction.

The fusion algorithm (§4.2.2) greedily scans the buffered window of pending tasks and finds the longest prefix satisfying all four constraints (a forward dataflow pass — familiar if you've implemented reaching-definitions or live-variable analysis), then builds one fused task whose argument list is the union of all stores touched (any store both read and written is promoted to Read-Write).

4 · Making fusion pay off — two supporting optimizations

Temporary elimination. Fusing tasks alone doesn't remove wasted allocations unless Diffuse can prove a store produced and consumed only inside the fused region can be demoted to a local, on-the-fly buffer. In the running example z = 2.0*x; w = y+z; v = w**2; norm = np.linalg.norm(w[len(w)//2:]) (Figure 6), only z qualifies after fusing lines 4–6: w doesn't (the still-pending norm task reads a slice of it later), v doesn't (the application still holds a live reference). Formally (Definition 4), a store is temporary in a fused prefix iff every read inside is preceded by a covering write inside, no later pending task reads/reduces it, and the application holds no live reference — tracked via a split reference-counting scheme separating application-held from Diffuse-internal references.

Memoization. Re-running the fusion analysis every loop iteration is wasteful if the task stream has the same shape each time, just with different store IDs. Diffuse recognizes this as an alpha-equivalence problem and canonicalizes each window to a De Bruijn-index-like numbering before comparing streams for isomorphism — two streams that canonicalize identically reuse the previous fusion decision (§5.2, Figure 7).

5 · Kernel fusion — turning fused tasks into fast code

Task fusion alone only removes runtime dispatch/allocation overhead — it doesn't make a task's inner loop faster. The paper found task fusion by itself gave no speedup on their benchmarks, because per-benchmark average task lengths (1.1–5.3 ms, Figure 9) already exceed Legion's roughly 1 ms per-task overhead threshold (§7, citing Task Bench). The savings have to come from the kernel level.

Library developers write a generator function per task (50–100 lines of C++, a one-time cost to library authors, §6.2) that emits an MLIR fragment for that task's body using the memref, affine, and arith dialects. When Diffuse fuses tasks, it builds one MLIR function containing each original task body spliced in program order, promotes distributed temporaries to task-local buffers (per §5.1), and runs standard polyhedral loop-fusion/parallelization passes to merge the separate loops into a single parallel loop — deleting the now-fully-local intermediate buffer — before lowering to GPU kernels or OpenMP (§6).

💡
Why this architecture is clean: it separates reasoning about distributed communication (§3–5) from reasoning about local loop optimization (§6) — the loop optimizer never needs to know anything is distributed at all, and facts from the distributed analysis (e.g. "these two arrays provably don't alias") can be handed directly to the MLIR passes to unlock better code (§6.4). The specific kernel-fusion technique (polyhedral loop fusion) is explicitly orthogonal — other techniques could be substituted in.
Follow the pipeline end to end

Tracing Figure 6 / Figure 8

z = 2.0 * x; w = y + z; v = w ** 2 — four-element distributed vectors, all identically partitioned (no aliasing).

① Fusibility (§4)

  1. Say x, y, z, w, v are all partitioned identically (same launch domain, same tiling) — no aliasing between them.
  2. Checking the four constraints across MULT, ADD, POW: launch domains match; nothing is written and then re-read/written through a different partition (true-dependence passes); nothing is read then written elsewhere (anti-dependence passes); no reductions are involved.
  3. All three are fusible per Definition 3 — every point's output depends only on the same point's inputs, never a neighbor's.

② Temporary elimination (§5.1)

  1. Is z temporary? It's entirely produced by MULT inside the fused region and consumed only by ADD, also inside the region (condition 1).
  2. Nothing after the fused prefix reads or reduces it (condition 2).
  3. If the application dropped its Python reference to z (as in the paper's del), condition 3 holds too — so z can be demoted from a real distributed array to a scratch buffer.
📌
In the paper's own trace, w survives as non-temporary only because a later norm task still reads part of it. In this simplified 3-line version without that extra read, w would also qualify.

③ Kernel-level fusion (§6, Figure 8)

Using Figure 8's actual two-task example, c = a+b; e = c+d — same mechanics, fewer variables. Each generator emits an MLIR loop like for i in 0..dim: c[i] = a[i] + b[i].

  1. Fusing splices both loops into one function in program order — still two separate affine.for loops back to back.
  2. Temporary elimination turns the distributed c into a stack-local memref.alloc.
  3. Polyhedral fusion merges the two loops into one parallel loop computing e[i] = (a[i]+b[i]) + d[i] per iteration, with the intermediate value for c[i] never written to memory at all.
  4. Concretely (illustrative numbers, not in the paper) — for a=[1,2,3,4], b=[5,6,7,8], d=[1,1,1,1]: unfused, you'd write c=[6,8,10,12] to memory, then read it back to compute e=[7,9,11,13] — two full memory passes. Fused, one pass computes e[i]=a[i]+b[i]+d[i] directly, e.g. e[0] = 1+5+1 = 7 — same result, zero passes over c.
⚠
Common mistake: assuming fusion changes what is computed. It doesn't — Theorem 1's whole point is that dependencies (and hence results) are preserved; only how many passes over memory / how many distributed tasks it takes changes.

Check your understanding

Practice

Try each before opening the answer.

Q1
Why does the stencil example (Figure 1) fuse the four additions and the multiply, but not the final copy center[:] = work?
Show answer
The four adds and the multiply operate on distinct partitions/views (north, east, west, south, and the scalar multiply's result) with no write-then-aliased-read pattern among them, so they satisfy all four fusion constraints. But center aliases the same underlying store as those views; fusing the write into the task that reads them would create simultaneous read/write access to overlapping data across processor boundaries — exactly what the anti-dependence constraint (and Definition 3) forbid (§2, §4.2.1).
Q2
What does "scale-free" mean for Diffuse's IR, and why does it matter?
Show answer
The size of the representation (partitions, index tasks) doesn't grow with the number of processors/GPUs — a partition is a symbolic function, not an explicit table; an index task stores a symbolic launch-domain shape, not per-processor entries. This matters because the fusion analysis runs on every batch of buffered tasks; if checking fusibility scaled with machine size, the analysis itself would become the bottleneck at high GPU counts (§3, §4.4).
Q3
The fusion constraints are described as "sound but not complete." What do those two terms mean here, and which one does Theorem 1 establish?
Show answer
Sound means: if the constraints say a sequence is fusible, it really is safe (no missed cross-processor dependence). Complete would mean: every actually-safe sequence is detected. Theorem 1 proves soundness only — by contradiction: assuming an undetected dependence exists, one of the four constraints would have had to fail. The paper explicitly disclaims completeness, noting application-specific knowledge could find more fusion opportunities (§4.2.1, §4.3).
Q4
In z = 2*x; w = y+z; v = w**2, why is z temporary but v is not, even though both are "produced inside" the fused task?
Show answer
Definition 4's third condition requires no live application references. z is deleted by the program before any pending task outside the fused prefix could read it, satisfying all three conditions. v is still referenced by the application after the fused region — the program could still launch a task reading v later — so it fails condition 3 and must remain a real distributed allocation (§5.1).
Q5
Why did task fusion alone (without the MLIR kernel-fusion step) fail to produce speedups in the paper's own check?
Show answer
Task fusion only removes per-task dispatch/allocation overhead. The benchmarks' tasks average 1–5 ms (Figure 9), already above Legion's roughly 1 ms minimum effective task granularity — so there isn't much per-task overhead left to remove. The actual gains come from kernel fusion (§6), which reduces passes over memory and increases arithmetic intensity — a fundamentally different kind of saving.
Q6
The CFD benchmark gets a larger speedup on 1 GPU than on 128 GPUs. Why doesn't more parallelism help fusion here?
Show answer
On a single GPU, the data isn't partitioned at all, so there's no aliasing between sub-stores held by different processors, and longer sequences of tasks can satisfy the fusion constraints. Once the array is partitioned across many GPUs, boundary/aliasing dependencies between neighboring partitions block some of the fusion that was possible in the unpartitioned case (§7.1).

Glossary, limitations & further reading

Core terms
Task-based runtimeA system (e.g. Legion) that a library targets by issuing tasks — units of work over data — rather than directly managing parallelism/communication itself.
StoreDiffuse's term for a distributed array — an ID plus a rectangular shape.
PartitionA symbolic mapping from points of a domain to sub-stores; None (replicated) and Tiling (affine block, possibly with a projection) are the two kinds discussed.
Index task / point taskAn index task is a whole SPMD-style group of parallel tasks over a domain; a point task is the single task at one point of that domain.
Dependence map D(T₁,T₂)Maps each point of T₁'s domain to the set of points in T₂'s domain whose execution depends on it.
Fusibility (Definition 3)T₁, T₂ are fusible iff every point's dependence is at most on the same point — no cross-processor dependence.
Sound but not completeThe fusion constraints never approve an unsafe fusion (sound), but may reject some safe ones (incomplete).
Temporary store eliminationDemoting a store from a real distributed allocation to a task-local buffer once it's proven invisible outside the fused task.
Supporting terms
Projection functionA function applied to a partition's domain points before tiling, used to express aliased/replicated data (e.g. the stencil's shifted views).
Memoization via alpha-equivalenceRecognizing that two task-stream windows have the same shape up to renaming of store IDs (via De Bruijn-style canonicalization), to reuse a previous fusion decision.
MLIR / dialectCompiler infrastructure whose programs mix typed sub-languages (dialects, e.g. memref, affine, arith) that shared passes can optimize and lower together.
Weak scalingAn experiment design where problem size grows with machine size so per-processor work stays constant; the reported metric is per-processor throughput.
Geo-mean (geometric mean)The summary statistic the paper uses to aggregate speedups across benchmarks — appropriate for ratios, unlike an arithmetic mean.
cuPyNumeric / Legate SparseDistributed, GPU-accelerated drop-in replacements for NumPy and SciPy-sparse, built on Legion — the two libraries Diffuse was integrated into.
PETScAn established MPI+C library for distributed sparse linear algebra, used as a hand-written performance baseline.
True / anti / reduction dependenceThe three classic hazards (RAW/WAW-like, WAR-like, and reduction-vs-read/write) that a dependence between two overlapping sub-stores can fall under (Definition 1).
Limitations & open questions
📌
Stated by the authors: the four fusion constraints are explicitly sound-but-incomplete (§4.2.1) — an analysis with domain/application-specific knowledge could fuse more than Diffuse does. Library developers must hand-write an MLIR generator function per task (50–100 lines of C++, §6.2) — a one-time cost per operation, described only qualitatively as "modest." Section 3.1 presents only None and Tiling partitions "for simplicity," asserting the full implementation supports more "with no additional technical insights" — an author assertion, not independently substantiated. The paper does not ablate temporary elimination or memoization (§7), arguing the former is "essential for speedup" and the latter "a requirement for a practical implementation" — reasonable, but no per-optimization quantitative evidence exists.
🔍
Other open items: no experimental head-to-head with the closest prior work (Sundram et al. 2022) because that implementation targets an older, no-longer-comparable cuPyNumeric — instead the paper reports informally (no numbers) that task-fusion-alone gave no speedup on their benchmarks. All reported experiments are weak-scaling only (§7) — strong-scaling behavior for a fixed problem size isn't reported. Diffuse is not a general parallelizing compiler — it assumes the input task stream is already implicitly parallel and doesn't address automatic parallelization (§1).
