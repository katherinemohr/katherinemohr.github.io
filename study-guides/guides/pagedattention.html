Handing out memory a block at a time, not a worst case at a time

Every LLM request used to reserve memory sized for the longest answer it might ever give — then almost never gave one that long. PagedAttention borrows a sixty-year-old OS trick to fix it, and triples serving throughput in the process.

Before you begin

The ML you need, and nothing more

You have the OS background this paper assumes (virtual memory, paging, fragmentation, copy-on-write, buddy allocation, gang scheduling) — no primer needed there. These four cards cover the ML side. Collapsed by default; open whatever's unfamiliar.

1What an LLM does at serving time — autoregressive generation▾

A language model is a function that, given a sequence of tokens (word pieces drawn from a vocabulary of tens of thousands), outputs a probability distribution over the next token. Generation is a loop: feed in the prompt, sample one next token, append it, feed the extended sequence back in, sample again — until an end-of-sequence token or a length cap. This is autoregressive generation (Section 2.2).

Each request has two phases: prefill (all prompt tokens known up front, processed in parallel — compute-dense matrix–matrix work) and decode (one new token per iteration — matrix–vector work, severely underutilizes the GPU, and is memory-bound). Decode dominates a request's latency (Section 2.2).

Because decode is memory-bound, the throughput lever is batching: run many requests' decode steps together so streaming the model weights is amortized across requests. Batch size is the throughput knob, and batch size is capped by how much memory each request's state consumes — that's the entire setting of this paper. (vLLM also adopts Orca's iteration-level scheduling, re-forming the batch after every token instead of per request — Section 2.3; orthogonal to this paper's contribution.)

Now you're ready: "memory per request" is the scarce resource this whole paper is about conserving.
2Attention, and why there are "keys" and "values" at all▾

A transformer is a stack of layers (OPT-13B has 40). The one piece that matters here is self-attention — how a token's computation reads information from all earlier tokens. For token position i, the layer computes three vectors from learned weight matrices: a query qᵢ ("what I'm looking for"), a key kᵢ ("what I offer to be matched on"), and a value vᵢ ("what I contribute if matched") — Eq. 2.

The attention output for position i is a weighted average of the value vectors at positions up to i, with weights from a softmax over dot products of qᵢ against the keys (Eq. 3):

a(i,j) = exp(qᵢ·kⱼ / √d) / Σₜ₌₁..ᵢ exp(qᵢ·kₜ / √d)
o(i)   = Σⱼ₌₁..ᵢ a(i,j) · vⱼ

Score how relevant each previous token j is to token i, normalize so the weights sum to 1, then blend the previous tokens' values by those weights.

🔑
Systems analogy: a key/value pair here is like a (tag, payload) entry in an associative cache — lookups score entries by match quality against a query. But unlike a cache lookup, attention doesn't select one matching entry; it takes a softmax-weighted blend of all entries. Every stored key and value participates in every lookup — which is exactly why per-token state can never be evicted piecemeal while a sequence is alive.
Now you're ready: attention is the only place a token's computation touches other tokens' state — the only computation vLLM had to rewrite.
3The KV cache — the object this whole paper is about▾

Generating the next token needs the keys and values of all previous positions, at every layer. They never change once computed, so serving systems compute each position's K/V once and cache it for the request's lifetime — the KV cache (Sections 1, 2.2). Its properties, from Sections 1 and 3:

  1. It's big. OPT-13B: 2 vectors × 5120 dims × 40 layers × 2 bytes (FP16) = 800 KB per token. At max length 2048, that's up to 1.6 GB for one request.
  2. It grows dynamically and unpredictably — one entry per generated token, and output length is unknown a priori.
  3. It's position- and history-dependent — "the" at position 5 differs from "the" at position 500. Sharing is only possible between sequences with an identical prefix.
  4. All of it is touched every iteration — a sequence's working set is its entire KV cache.
Now you're ready: from A100 to H100, FLOPS more than doubled while GPU memory capacity stayed flat (Section 3) — this problem gets worse, not better, with newer hardware.
4Decoding algorithms — where sharing opportunities come from▾

"Decoding algorithm" = the policy turning next-token probabilities into output text (Sections 3, 4.4):

  • Basic / greedy sampling: one output sequence. No sharing opportunity.
  • Parallel sampling: k independent samples from one prompt. All k share the prompt's KV cache exactly, diverging from the first generated token.
  • Beam search: keep the top-k partial sequences at every step; expand and re-prune. Beams constantly fork and die — "similar to the process tree created by compound forks" (the paper's own analogy).
  • Shared prefix / system prompt: many requests share a long instruction template — "like a shared library mapped into multiple processes" (again, the paper's analogy).
Now you're ready: prior systems could exploit none of this sharing, because each sequence's cache lived in its own contiguous buffer.
The whole story in one place

PagedAttention in a nutshell

The problem, the fix, and the result.

Serving an LLM is throughput-bound by GPU memory, not compute. Because deep-learning frameworks require tensors to be contiguous, and because an output's length is unknown in advance, prior serving systems (FasterTransformer, Orca) pre-allocated each request's whole KV cache for the maximum possible sequence length — one contiguous chunk, held for the request's entire lifetime (Sections 1, 3.1). Measured result: only 20.4%–38.2% of that memory ever held live token state (Fig. 2) — the rest lost to reservation, internal fragmentation, and external fragmentation. A memory-allocator failure mode any systems person recognizes instantly.

PagedAttention (Section 4.1) treats the KV cache the way an OS treats process memory: partition each request's cache into fixed-size KV blocks that need not be physically contiguous, and rewrite the attention GPU kernel to gather blocks through an indirection table. On top of it, vLLM's memory manager is a near-verbatim adaptation of demand-paged virtual memory — blocks ≈ pages, tokens ≈ bytes, requests ≈ processes. Block tables map logical to physical blocks; reference counting plus copy-on-write enable cross-sequence sharing; preemption is handled by swapping to CPU RAM or by cheap recomputation.

The payoff: vLLM raises KV-cache utilization to 96.3% and improves serving throughput 2–4× at the same latency versus FasterTransformer and Orca — with gains growing for longer sequences, larger models, and decoding algorithms that permit sharing. The attention kernel itself runs 20–26% slower (Section 7.1); the trade is overwhelmingly worth it, because the bottleneck was never the kernel.

🍯 Key takeaways

  • Prior systems pre-allocate for the worst case (max length); PagedAttention allocates on demand, one fixed-size block at a time.
  • The attention kernel is rewritten to read K/V through a block table — non-contiguous, but numerically identical to the original computation.
  • vLLM's memory manager is demand-paged virtual memory, transplanted: block table = page table, KV block = page.
  • Refcounts + copy-on-write let unrelated sequences share physical blocks — parallel sampling, beam search, shared prefixes.
  • Under memory pressure: swap evicted blocks to CPU RAM, or throw them away and recompute in one prefill pass.
  • Result: 96.3% KV-memory utilization (vs 20.4–38.2%) and 2–4× throughput, for a 20–26% kernel-level tax.
Six everyday pictures

How to think about vLLM's memory manager

The paper leans on OS analogies more than most — these are mostly the paper's own comparisons (Sections 1, 4.4, 8), each with an honest note on where the picture stops being true.

The core mapping · Demand paging

A process's virtual memory

An OS gives each process a contiguous virtual address space, but backs it with scattered physical pages via a page table — no process needs a physically contiguous chunk of RAM. vLLM does the same for a request's KV cache: logical blocks fill in order, but the block table maps each one to an arbitrary physical block anywhere in GPU memory (Section 1).

This mapping is unusually load-bearing here — it's the design, not a teaching aid. See "Where the analogy breaks," below, for the places it stops holding.
Parallel sampling · fork() + COW

Copy-on-write fork

fork() gives a child process the parent's memory pages without copying them — pages are shared (refcount > 1) and copied lazily, only when one side writes. Parallel sampling is exactly this: k samples share the prompt's physical blocks until a sample writes its first generated token into the shared, partially-filled last block — then vLLM copies just that one block (Section 4.4, Fig. 8).

Where it holds tightly: copying is bounded by (k − 1) blocks total, regardless of prompt length — every full prompt block is never copied at all.
Beam search · The process tree

Compound forks, forming a tree

Beam search keeps the top-k partial sequences at each step, and each step forks every surviving beam into candidates before pruning back to k — "similar to the process tree in the OS created by compound forks" (the paper's own phrase, Section 4.4). Beams share the prompt and interior blocks along common ancestry, diverging block-by-block; pruned beams simply free their logical blocks, decrementing refcounts.

Where it holds tightly: vLLM reduces what used to be large physical copies on every beam-set change to at most one COW block copy (Section 4.4).
Shared system prompt · Shared libraries

One .so, mapped everywhere

libc is compiled once and mapped read-only into every process that links it — not recompiled or duplicated per process. A provider pre-computes and caches physical blocks for a predefined prompt prefix; any request starting with it maps its initial logical blocks straight to the cached ones — "as how OS handles shared library across processes" (the paper's phrase, Section 4.4) — skipping both the memory and the prefill compute for that prefix.

Where it's narrower: this only covers provider-predefined prefixes (Section 6.4) — automatically detecting shareable prefixes across arbitrary, unrelated requests is left open.
Recovery · Recompute instead of swap

Rebuilding instead of restoring from disk

Under memory pressure, an OS pages out to disk and pages back in — the contents are restored exactly. vLLM offers a second option an OS can't: throw the evicted KV cache away, and on resume, concatenate the prompt with the already-generated output tokens and rebuild the entire cache in one parallel prefill pass — instead of re-running the original token-by-token decode loop (Section 4.5).

Where it fully breaks: an OS cannot regenerate a page's contents from nothing. This works only because the KV cache is deterministic derived state — recoverable from tokens the system already has.
Where it breaks · No MMU

A page table with no hardware to walk it

An OS's address translation is accelerated by a hardware MMU and TLB, essentially free on the access path. There's no GPU-kernel equivalent — vLLM's block-table lookups run in software, inside the attention kernel itself. That's the entire source of the paper's 20–26% attention-kernel overhead (Section 7.1, 8): it's affordable only because attention is one operator among many, and the workload is memory-capacity-bound, not kernel-latency-bound.

Consequence: don't expect this trick to be free elsewhere — see "Where the OS analogy breaks" in the next tab.
The full explanation

How it actually works

Section by section, with an interactive block allocator you can drive yourself.

1 · The problem — a memory allocator designed by tensor libraries

Deep-learning frameworks mostly require tensors to occupy contiguous memory, so prior serving systems stored each request's whole KV cache as one contiguous tensor, pre-allocated for the maximum possible sequence length (e.g. 2048 tokens) since the true output length is unknown (Sections 1, 3.1). Figure 3 splits the resulting waste into three familiar categories: reserved slots (not-yet-generated tokens, held for the request's whole lifetime), internal fragmentation (the unused tail of a request that finishes early), and external fragmentation (holes between differently-sized chunks under a buddy allocator).

⚠
The oracle doesn't save you. Orca-Oracle — an infeasible baseline that magically knows every output length in advance — still only reaches 38.2% utilization (Fig. 2). Even an exactly-sized reservation can't be lent out mid-request, and different chunk sizes still fragment externally. Compaction is dismissed too: moving huge KV caches is too expensive on a performance-sensitive serving path, and per-request contiguous chunks would still block sharing anyway (Section 3.1).

Second problem: no sharing. Parallel sampling and beam search create sequences with identical or overlapping prefixes, but separate contiguous buffers make sharing impossible — prior systems duplicated the prompt's KV cache per sample and copied large regions whenever beams forked (Sections 1, 4.4).

2 · PagedAttention — making the attention kernel indirection-tolerant

Chop each sequence's KV cache into KV blocks of fixed block size B tokens (default 16; Section 7.2). Store blocks anywhere in GPU memory. During attention, the kernel walks the sequence's blocks one at a time — fetch block j's keys, score the query against them, fetch block j's values, accumulate the weighted sum — locating each block via the block table (Section 4.1, Fig. 5). With key block Kⱼ and value block Vⱼ, the per-token equation becomes a block-wise one:

# same computation as before, just grouped by block
A(i,j) = exp(qᵢ·Kⱼ / √d) / Σₜ₌₁..⌈i/B⌉ exp(qᵢ·Kₜ·1 / √d)
o(i)   = Σⱼ₌₁..⌈i/B⌉ Vⱼ · A(i,j)ᵀ

This is not an approximation — it computes the same attention, just restructured over scattered extents, "without affecting the model accuracy at all" (Section 1). One implementation detail: a token has K/V per layer and per attention head; vLLM manages these in separate blocks with separate block tables purely for convenience — no performance difference either way (Section 4.1, footnote 1).

💡
The cost, and why it's paid gladly: block-table lookups and variable-length handling cost the attention kernel 20–26% versus the FasterTransformer kernel it's adapted from (Section 7.1). Countermeasures: a fused reshape+block-write kernel, a fused block-read+attention kernel with one GPU warp per block for coalesced access, and batched COW copies in a single kernel launch (Section 5.1). The overhead is confined to attention; the model's other (larger) operators are untouched.

3 · vLLM's KV cache manager — demand paging, nearly verbatim

The mapping is unusually load-bearing (Section 1): blocks are pages, tokens are bytes, requests are processes. A request's KV cache is a sequence of logical KV blocks, filled left to right; a block engine pre-carves GPU DRAM (and CPU RAM, for swap) into physical KV blocks; the KV cache manager keeps per-request block tables mapping logical → physical blocks with fill counts. Allocation is on demand — a new physical block only when the previous one is full, no reservation for the maximum length (Sections 4.2–4.3).

Waste per request is confined to at most one partially-filled block. That's how Fig. 2's 96.3% happens, and it converts directly into batch size: vLLM batches 2.2× more concurrent requests than Orca-Oracle and 4.3× more than Orca-Max on the ShareGPT trace (Fig. 13a). Block size B is a classic page-size trade-off — too small and the GPU can't process the cache with enough parallelism; too large and internal fragmentation grows while the odds of a block being shareable drop (Section 7.2, Fig. 18b). Try both trade-offs yourself below.

4 · Sharing — refcounts, copy-on-write, shared libraries

One physical block can back multiple logical blocks in different sequences. Each physical block carries a reference count; writes to a shared block go through block-granularity copy-on-write (Section 4.4). Measured savings (Section 6.3, Fig. 15): parallel sampling saves 6.1%–9.8% of KV memory on Alpaca (16.2%–30.5% on ShareGPT); beam search saves 37.6%–55.2% on Alpaca (44.3%–66.3% on ShareGPT). The exposed API is minimal: fork, append, free on sequences (Section 5.2). Because the executing kernel only ever sees lists of physical block IDs, requests running different decoding algorithms batch together freely — sharing complexity stays hidden behind the translation layer.

5 · Scheduling, preemption, and what replaces the page fault

Demand allocation with unknown output lengths means vLLM will run out of physical blocks under load (Section 4.5). Policy: FCFS admission; under pressure, the latest-arrived requests are preempted first, so early requests are never starved. Eviction granularity: all or none of a sequence's blocks — since a live sequence accesses all its blocks together, partial eviction just guarantees an immediate fault. Sequences that may share blocks form a sequence group, gang-scheduled together.

Recovery has two options. Swapping: copy evicted blocks to a CPU-RAM pool; vLLM stops admitting new requests until all preempted sequences complete, so the swap pool never needs to exceed the GPU's KV allocation. Recomputation: discard the evicted cache; on resume, concatenate the prompt with already-generated output and rebuild the entire cache in one prefill iteration rather than re-running token-by-token decode. Measured (Section 7.3, Fig. 19): recomputation is more efficient at small block sizes (swapping can't reach effective PCIe bandwidth with many tiny transfers), swapping wins at large ones, and the two are comparable for medium sizes (16–64).

6 · Distributed execution

For models spanning multiple GPUs, vLLM uses Megatron-LM-style tensor model parallelism: each worker holds a shard of every layer and synchronizes with all-reduce (Section 4.6). Since all workers process the same token positions, a single KV cache manager in the centralized scheduler holds one logical→physical mapping shared by every worker; each worker stores only its attention heads' share of K/V at those physical block IDs. Workers receive token IDs plus block tables each step and never coordinate on memory among themselves.

Where the OS analogy breaks

Section 8 is unusually candid about scope:

⚠
No hardware MMU. Address translation runs in software inside the GPU kernel — the source of the 20–26% attention overhead. Affordable only because the workload is memory-capacity-bound, not kernel-latency-bound.
⚠
Recomputation has no OS counterpart — an OS can't regenerate a page's contents — and all-or-nothing eviction exploits certain knowledge (the whole working set is accessed together) an OS never has.
⚠
Don't apply this everywhere. For DNN training (static shapes, plannable allocation) or compute-bound serving, extra indirection and non-contiguous memory may degrade performance. Paging earns its keep only where allocation is dynamic/unpredictable and performance is memory-capacity-bound.
Follow the numbers, step by step

One request, by the numbers

All model constants from Section 3 (OPT-13B): 40 layers, hidden size 5120, FP16, max length 2048. Block size B = 16 (Section 7.2). The percentages below are illustrative arithmetic from those constants, not numbers reported verbatim by the paper (except step 1, which is the paper's own calculation).

① Per-token KV cost (the paper's own number)

  1. 2 (K and V) × 5120 (hidden dims) × 40 (layers) × 2 bytes (FP16) = 819,200 bytes ≈ 800 KB per token (Section 3).

② The request: 200-token prompt, 100 generated tokens

  1. Total live state: 300 tokens × 800 KB ≈ 234 MB.
  2. Old world (Orca-Max-style): pre-allocate 2048 contiguous slots ≈ 1.6 GB, held for the request's whole lifetime.
  3. Utilization at completion: 300 / 2048 ≈ 14.6% — the other ~1.37 GB is internal fragmentation plus reservation, room that could have held five more identical requests. External fragmentation from mixed chunk sizes comes on top.
⚠
Common mistake: assuming smarter length prediction fixes this. Fig. 2 shows Orca-Oracle, with perfect length knowledge, still keeps only ~38% of KV memory live — an exactly-sized reservation is still unusable by others while the request runs, and holes remain between differently-sized chunks.

③ vLLM: allocate in blocks of 16

  1. 300 tokens need ⌈300/16⌉ = 19 blocks: 18 full, the last holding 300 − 288 = 12 of 16 slots.
  2. Waste: 4 slots ≈ 3.2 MB → utilization ≈ 98.7%.
  3. Allocated incrementally: before generation started, only ⌈200/16⌉ = 13 blocks existed.
  4. On completion, all 19 blocks free immediately for other requests (Section 4.3) — nothing lingers the way the old world's 1.6 GB did.

④ Add parallel sampling, k = 3

  1. All three samples map their 12 full prompt blocks (192 tokens ≈ 150 MB) to the same physical blocks — refcount 3.
  2. Only the 13th, partially-filled prompt block gets copy-on-write as the samples diverge (Section 4.4).
  3. Prompt storage is paid once instead of three times — saving ~300 MB on this single request.
  4. For scale: in the paper's own experiments, prompt KV was ~12% of total KV memory, and total sharing savings were 6.1–9.8% on Alpaca, 16.2–30.5% on ShareGPT (Section 6.3).

Check your understanding

Practice

Try each before opening the answer.

Q1
Two requests both contain the word "server" — can vLLM back those two tokens' KV entries with the same physical storage?
Show answer
No. A token's K/V vectors depend on its entire prefix, not on token identity — "server" at position 12 of one prompt and position 40 of another has different KV state (Section 2.2). Sharing is only valid between sequences with an identical prefix, which is exactly why every sharing mechanism in the paper (parallel sampling, beam search, shared system prompt) is a prefix-sharing mechanism.
Q2
Why does vLLM evict all of a sequence's blocks or none, instead of running LRU over blocks?
Show answer
Every decode iteration reads all of a sequence's KV blocks (attention sums over every previous position), so a scheduled sequence's working set is its entire cache. Evicting part of it guarantees a "fault" on the very next iteration. LRU-style recency heuristics exist because an OS can't know future access patterns; vLLM knows them exactly, so it uses all-or-nothing eviction and gang-schedules sequence groups (Section 4.5).
Q3
Orca-Oracle knows every request's exact output length in advance — no over-reservation for length. Why does vLLM still beat it by 1.7×–2.7× on ShareGPT?
Show answer
Three problems survive perfect length knowledge (Sections 1, 3.1, 6.2; Fig. 2): (1) even an exactly-sized contiguous chunk is reserved for the request's whole lifetime, so not-yet-filled slots can't be lent to others; (2) variable chunk sizes still cause external fragmentation under the buddy allocator; (3) contiguous per-sequence buffers still preclude cross-sequence sharing. Orca-Oracle's live-token share of KV memory is still only ~38% vs. vLLM's 96.3%.
Q4
Recomputing an evicted sequence's KV cache can be much cheaper than the computation that originally produced it. What breaks the symmetry?
Show answer
The original cache was built incrementally by the sequential decode loop — one memory-bound matrix–vector step per token. On recovery, all tokens (prompt + already-generated output) are known, so they can be concatenated into a "new prompt" and processed in a single prefill iteration with parallel matrix–matrix compute (Section 4.5). That, plus swapping's poor PCIe efficiency at small block sizes, is why recomputation wins at small block sizes and stays comparable to swapping at medium ones (Section 7.3).
Q5
Your colleague proposes PagedAttention-style block management for a vision-model serving fleet with fixed-size image inputs. Good idea?
Show answer
Probably not, and the paper says so (Section 8). Fixed input shapes mean allocation is static and can be planned ahead of time, and if the workload is compute-bound rather than memory-capacity-bound, extra memory indirection adds overhead (recall the 20–26% attention-kernel tax) without unlocking any batch-size headroom. Paging pays off only under dynamic, unpredictable allocation and memory-bound performance.
Q6
In parallel sampling with k samples, how much copying does copy-on-write actually do, and when?
Show answer
At most one block copy per sample that writes into the shared, partially-filled last prompt block while its refcount exceeds 1 — the final writer finds refcount 1 and writes in place, and every full prompt block is never copied at all (Section 4.4, Fig. 8). So the copied data is bounded by (k − 1) blocks regardless of prompt length. vLLM batches these small copies into a single fused kernel launch rather than many cudaMemcpyAsync calls (Section 5.1).

Core terms
TokenThe unit of LLM text I/O — a word or word fragment. Also the granularity at which the KV cache grows.
Self-attentionHow position i reads earlier positions: score each earlier token's key against i's query, softmax, take the weighted average of values (Eq. 3).
KV cacheThe stored keys and values of all processed tokens, across all layers — 800 KB/token for OPT-13B; read in full every decode step.
Prefill / decode phasePrefill processes the whole prompt in parallel (compute-dense); decode generates one token per iteration (memory-bound) — Section 2.2.
KV blockvLLM's fixed-size unit of KV cache (default B = 16 tokens' K/V) — the "page" of the design (Section 4.1).
Block tablePer-request mapping from logical KV blocks to physical KV blocks, with fill counts — the "page table" (Section 4.2).
Sequence groupThe sequences of one request (e.g. all beam candidates) that may share blocks and are gang-scheduled (Section 4.5).
Copy-on-write (COW)Shared physical blocks are copied only when one sequence writes to them — at block granularity (Section 4.4).

Swapping vs. recomputationTwo ways to recover a preempted sequence's evicted KV cache — copy to CPU RAM, or rebuild it in one prefill pass (Section 4.5).
FasterTransformer / OrcaThe baselines: NVIDIA's latency-optimized inference engine, and the (non-public) throughput-oriented system that introduced iteration-level scheduling.

Limitations & open questions
📌
Stated by the authors: the technique targets workloads that are memory-bound with dynamic, unpredictable allocation — for DNN training or compute-bound serving, the indirection overhead may degrade performance (Section 8). The kernel-level cost (20–26% on the attention operator) is an accepted, not eliminated, tax. Block size is a tuned constant (16), not adaptive per workload (Section 7.2).
🔍
Not much discussed (observations, not the paper's claims): the swap design admits no new requests while any preempted sequence is outstanding (Section 4.5) — simple and starvation-free, but potentially conservative under bursty load. The evaluation is throughput-centric — no tail-latency (p99) analysis, and time-to-first-token vs. inter-token latency aren't separated. Numbers come from A100-class hardware and 2023-era dense models; constants like 800 KB/token shift with newer models and attention variants. Shared-prefix caching is evaluated only with provider-predefined prefixes (Section 6.4) — automatic detection is left open. The chatbot experiment doesn't retain KV cache across conversation rounds (Section 6.5) — cross-turn caching is another open question.
